# Движок в шлеме: миры движка внутри Meta IWSDK

Версия спеки: 1.0 (пять раундов критики luna, см. `research/spec_crit_log_xr.md`; оценки 4/4, 3/4, 4/4, —, 5/6).

Цель: мир, который собирает `engine/`, открывается в шлеме Quest через Meta Immersive Web SDK (IWSDK, `app/`): стерео, голова, руки, локомоция Meta, эмулятор IWER для проверки без железа. Движок остаётся хозяином мира (геометрия, нав, двери, режиссёр, NPC), IWSDK становится хозяином страницы (XR-сессия, цикл кадров, камера = голова, ввод, UI). Нужно к VR Start (18 ноября); сабмит Meta AI 4 ноября идёт на десктопном рантайме и этой спекой не трогается.

Закрывает парковку `P2` в `LESSONS.md` («Сцены движка в Meta VR»).

### Общие правила

- **Граница.** `engine/` не импортирует `@iwsdk/*` и остаётся на обычном `three`: десктопный рантайм, `dreamer check`, `shots` и все тесты движка работают как раньше. `app/` импортирует движок по относительному пути и three берёт только из `@iwsdk/core` (правило `app/AGENTS.md`); одна three обеспечивается alias'ом из F2, его не убирать.
- **Ввод, камера, кадр — у IWSDK.** Код в `app/` не пишет в `world.player.position` и `world.camera` напрямую (F4); игрок ставится через `LocomotionSystem.setPlayerPosition`.
- **Проверка без железа — IWER через `@iwsdk/cli`** (`dev up --headless --allow-browser-automation`, `xr enter`, `xr set-gamepad-state`, `xr run-sequence`, `browser screenshot`, `browser run` со скриптом на `frame`). Утверждение про позу, руки или взаимодействие требует активной XR-сессии (`xr status` → `sessionActive: true`), плоский скриншот вне XR этого не доказывает.
- Перед правкой `app/` — skill `iwsdk-dev` (правило `app/AGENTS.md`), для рук и луча — `iwsdk-grab`/`iwsdk-ray`, для отладки систем — `iwsdk-debug`.
- Сначала красный тест, потом код. В `app/` нет vitest: проверки фазы — скрипт `app/tools/xr-check.mjs` (появится в X2) под `iwsdk browser run`, он печатает JSON и падает с ненулевым кодом. Тесты движка — vitest, как везде.
- Никаких `npm install`: в `app/` и `engine/` уже есть всё нужное (`@iwsdk/core` 1.1.0-rc.2, `@iwsdk/cli`, `super-three` 0.185, `three` 0.185). Живых вызовов моделей нет.
- В `update()` систем IWSDK не выделять память (правило `app/AGENTS.md`; в спайке это нарушено ради скорости, X3 чинит).
- Новая публичная функция или модуль — строка в `research/feature_map.md` в том же коммите.
- Миры для `app/public/worlds/` не коммитятся (там симлинки на `dist`), в `.gitignore`.

**Срок X1.** X1 меняет `start()` десктопного рантайма, на котором идёт сабмит 4 ноября (21:00 ET). X1 начинается **после** сабмита. Перед X1 фиксируется эталон: `shots` спальни и один прогон `dreamer check --built` до правок, после X1 кадры совпадают попиксельно (допуск как в существующих тестах `shots`). До сабмита допустим только спайк в `app/`, он `engine/` не меняет.

**Порядок:** X1 → X2 → X3 → X4 → X5 → X6. **Минимум для VR Start — X1–X4:** мир в шлеме, ходьба стиком с забором, двери. Внутри X3 телепорт и жесты рук вынесены в необязательный подэтап X3б и в минимум не входят. X5 (режиссёр) — после минимума и может не успеть. X6 — бюджет Quest, финальная часть ждёт железа; минимальная цель замера на шлеме: спальня, кадр ≤ 13.9 мс (72 fps), срок — первый день доступа к железу.

## X1. engine: мир строится одной функцией `buildWorld`

Зоны: `engine/src/runtime/world.ts` (новый), `engine/src/runtime/main.ts`, `engine/src/runtime/outdoor.ts`, `engine/test/runtime-world.test.ts` (новый).

Сейчас вся сборка сцены зашита в `start()` в `main.ts` (рендерер, сцена, меши, GLB, свет, scatter, двери, walker, камера в одной функции); `materialOf`/`meshOf` приватные, поэтому спайк их скопировал. Нужно разделить «что в мире» и «чем показывать».

Контракт `buildWorld(data: { geo; nav; built?: Built }, opts: { base: string; hide?: Set<string>; loaders?: { maps; glb; scatter } }): Promise<EngineWorld>`:
- `EngineWorld.root: Group` — все меши, GLB (уже подменённые), свет, scatter; без рендерера, без камеры, без DOM;
- `EngineWorld.walker`, `EngineWorld.doors: Map<string, Door>`, `EngineWorld.objects: Map<string, Object3D>`, `EngineWorld.spawn: { x, floorY, z, yawDeg }`;
- `EngineWorld.shell: Object3D[]` — меши `kind ∈ {floor, wall, cap}` (то, что пойдёт в локомотор, F7);
- `opts.hide` вычисляет вызывающий: `main.ts` берёт `setup.hide` из `pickCamera` (`runtime/cams.ts`, `main.ts:158–164`), поведение URL-режимов камеры не меняется;
- `opts.base` — префикс к относительным `map` и `glb` (в спайке `./worlds/<name>/`);
- `EngineWorld.geo`, `.nav`, `.layers`, `.built` — исходные данные, нужные `main.ts` для `startStage` и `bridge` (`stage/index.ts:18`, `main.ts:252,279`);
- `EngineWorld.style` — `ambient`, `exterior` из `geo.style`; применяет хост. `tone`/`exposure` сборка в `geometry.json` не пишет (`build/geometry.ts:310` — только `ambient`, `exterior`), поэтому на практике `main.ts:135–138` всегда берёт значения по умолчанию. Контракт: константы `TONE = Neutral`, `EXPOSURE = 0.9` живут в `world.ts`, `geo.style.tone === "none"` отключает (как сейчас); новых полей в схему не добавляем.
- `EngineWorld.shadows: boolean` — есть ли у солнца `castShadow` (`main.ts:157–205`); `buildWorld` расставляет `castShadow/receiveShadow`, а `renderer.shadowMap` включает хост. В XR тени по умолчанию выключены (бюджет Quest), включаются флагом хоста.
- `buildWorld` включает outdoor (небо, земля, солнце, полусферический свет). Сейчас `addOutdoor(scene, …)` кладёт объекты в `Scene` и меняет `scene.background` (`outdoor.ts:121–146`): его переделать так, чтобы он возвращал `{ objects, background }`; объекты идут в `root`, `background` — в `EngineWorld.background: Color | null`, применяет хост. `opts.base` применяется также к GLB `scatter` и к файлам outdoor (`main.ts:216–223`). `loaders.scatter` — отдельный загрузчик целой GLTF-сцены (scatter обходит меши и запекает матрицы, `main.ts:211–230`; `loadGlb` подгоняет модель под placeholder и для него не годится); `loaders.glb` — для мешей `geo.meshes`.
- `built` необязателен (`{}` по умолчанию, как `main.ts:125–130`), пустые слои нава дают пустой слой (`main.ts:241–247`).
- `EngineWorld.loads: { ok, total, failed }` — все подмены GLB (меши и `scatter`), заглушка при сбое остаётся.
- `opts.loaders?: { maps, glb }` — загрузчики подставляются (по умолчанию `loadMaps`/`loadGlb`); «без DOM» значит: ни рендерера, ни камеры, ни DOM-узлов внутри `buildWorld`, текстуры и GLB идут через переданные загрузчики. Гарантия vitest: фикстура без outdoor и без `scatter`, загрузчики-заглушки (реальные `loadGlb`/outdoor создают `canvas` через `document`, `assets.ts:81–108`); пути с реальными загрузчиками проверяет `xr-check.mjs` и браузерный прогон десктопа.
- Двери собираются внутри `buildWorld` (нужны слои нава и walker); `bridge`, `stage`, клавиатура, `touchTarget` остаются в `main.ts`.

`main.ts` вызывает `buildWorld` и дальше делает только своё: рендерер, камера, клавиатура, `frame`, `__dreamer`. Хуки хозяина (`__dreamer.three`, `__dreamer.onFrame`, `frameHooks`) не трогать.

`root` содержит: меши и подменённые GLB (источник `geo.meshes`, `main.ts:162–189`), свет (`addSceneLights`), outdoor (`geo.outdoor`), scatter (`built.scatter`, `main.ts:192–236`). `objects` — карта по `id` меша из `geo.meshes`.

Регрессия десктопа после X1 (кроме совпадения кадров): `__dreamer` и его хуки, `?stage=`, `?cam=` режимы со `hide`, `markNoblock`, сбой GLB оставляет заглушку-меш, `__ready` после всех GLB.

Тесты: (0) `visible` и `markNoblock` сохраняются после GLB-подмены, тени GLB и `scatter`, отказ загрузчика оставляет заглушку; (1) `buildWorld` (загрузчики-заглушки) на фикстуре `h0/make/testdata/world_run/dist`: для каждого `id` из `geo.meshes` в `objects` есть объект (и после GLB-подмены, дочерние меши GLB не считаются), `shell` содержит только `floor/wall/cap`, свет и scatter считаются отдельно; (2) старые тесты рантайма и `shots` зелёные без правок; (3) `spawn` совпадает с тем, что раньше ставил `syncCamera`.

## X2. app: хост мира движка

Зоны: `app/src/engine-host.ts` (из спайка, переписать на `buildWorld`), `app/package.json` (скрипт `xr:check`), `app/src/index.ts`, `app/vite.config.ts`, `app/tsconfig.json`, `app/tools/xr-check.mjs` (новый), `.gitignore`.

- Хост грузит `geometry.json`, `nav.json` и `build.json` (при ошибке `build.json` — `{}`, как `main.ts:125–130`), вызывает `buildWorld`, кладёт `root` одной сущностью `world.createTransformEntity(root)`; сущности оболочки для локомотора создаются с `{ parent: rootEntity }` — без этого IWSDK переподчиняет меш активному уровню (`ecs/world.js:176–179`) и `root` теряет оболочку (в спайке так и было, при тождественных трансформах это не видно); применяет `style` к `world.renderer`/`world.scene`, ставит игрока через `setPlayerPosition` и `player.rotation.y = yawDeg·π/180 + π` (F5).
- Выбор мира (F9): `?world=` из URL, иначе `localStorage['dreamer.world']` (ключ спайка `xrspike.world` — черновой, без миграции), иначе `import.meta.env.VITE_DREAMER_WORLD`. `iwsdk.config.json` для этого не трогаем: это файл проекта IWSDK, его правка перезапускает Vite. Без мира — старая сцена сплатов как сейчас.
- `oneThree`: хост берёт меши, созданные внутри `buildWorld` (`root`, любой `Mesh`), и проверяет `instanceof` относительно классов `@iwsdk/core`, а не только собственные импорты хоста.
- Отчёт `window.__dreamerXr` (вместо `__xrspike`; хост заполняет его после `buildWorld`): `oneThree`, `meshes`, `glb`, `shell`, `spawn`, `player`, `offNav`, `ready`.
- Ошибки: любой сбой `fetch`/`buildWorld` хост ловит и публикует в `__dreamerXr.error: string` (отчёт создаётся до загрузки, `ready: false`); `xr-check.mjs` при непустом `error` завершается сразу с кодом 4.
- Готовность: `ready: true` ставится после подмены всех GLB (как `__ready` на десктопе, `main.ts:431–436`); `glb: { ok, total, failed }`.
- Схема отчёта: `oneThree: boolean`, `meshes: number`, `glb: {ok,total,failed}: number` (из `EngineWorld.loads`, GLB `scatter` включены), `shell: number`, `spawn: [x, floorY, z, yawDeg]` в метрах и градусах, `player: [x, y, z]` в метрах, `offNav: number`, `ready: boolean`. «Игрок на спавне» = |Δx|, |Δz| ≤ 5 см и |Δy| ≤ 2 см (yaw не сравнивается).
- Вход в XR оркестрирует `npm run xr:check` (цепочка `iwsdk` CLI: `dev up` → `xr enter` → `browser run app/tools/xr-check.mjs` → `xr status` → `xr exit`); сам скрипт страницы сессию не открывает. Приёмка: вход через кнопку приложения (`offer: "always"`) или `xr enter`, после выхода страница жива, отчёт доступен.
- `engine-host.ts` не импортирует `three` напрямую (правило `app/AGENTS.md`): `oneThree` сравнивает объекты из `buildWorld` с классами `Group`/`Mesh` из `@iwsdk/core`.
- `app/tools/xr-check.mjs`: опрос каждые 250 мс, таймаут 60 с (код 2), ненулевой `glb.failed` (код 3), провал проверки (код 1). Под `iwsdk browser run` (на `frame`, F10) ставит мир, ждёт отчёт, проверяет `oneThree === true`, все GLB загружены, игрок на спавне ±5 см, `xr enter` → `sessionActive`. Ненулевой код при провале.

## X3. ходьба: локомотор Meta + нав движка без дрожания

Зоны: `engine/src/nav/fence.ts` (новый), `engine/src/build/write.ts` (`fence` в `nav.json` или отдельный файл), `app/src/engine-host.ts`, тесты.

Спайк показал, что гибрид работает (F7), но страж откатывает игрока каждый кадр (F8). Решение: отдать нав движка локомотору как геометрию, а не как поправку.

- `buildFence(nav, insetM): Float32Array` — вход только `nav.json` (слои: `level`, `y`, `origin`, `w`, `h`, `bits`; `nav.doors`): категорий запрета в bitmap нет и не нужно, берётся граница «проходимо | непроходимо». Формат: треугольники по 9 float (x,y,z ×3), метры, мировая система; для каждого ребра между проходимой и непроходимой клеткой слоя — квад (2 треугольника) от `layer.y` до `layer.y + 2.0`, нормаль в сторону проходимой клетки, сдвиг ребра на `insetM` в сторону непроходимой. Клетки за краем сетки слоя (`origin`, `w`, `h`) считаются непроходимыми — у края забор есть. Клетки дверей из `nav.doors` считаются проходимыми для забора, их закрывает створка (X4: створка — `LocomotionEnvironment` типа `kinematic`). Слои этажей строятся независимо, `makeWalker` проверяет рампы раньше bitmap (`walk.ts:44–53`), `nav.ramps[].poly` хранится отдельно от `layers[].bits` (`grid.ts:432–446`): забор использует ту же функцию, что рантайм (`rampWalkable`, уже экспортирована из `nav/floor.ts:116`): проходима только центральная полоса рампы шириной `poly − 2 × CAPSULE_R`, а не весь полигон. Тесты: вход на рампу и выход с неё не упираются в забор. `insetM = 0.5` (радиус капсулы IWSDK): маска нава уже раздута на `CAPSULE_R` 0.25 м, поэтому любая запрещённая полоса шире 0.5 м и сдвиг на 0.5 м остаётся внутри неё; центр игрока доходит до границы нава, как в спайке. Квантование клетки 4 см даёт допуск ±4 см в тестах. Стены оболочки локомотор тоже держит на 0.5 м, у нава 0.25 м — это допустимо (игрок не ближе), но проходы уже 1.0 м IWSDK не пропустит: в приёмке проверить ширину каждой двери комнаты (поле `width` двери в `built.doors[].width` (формируется `build/doors.ts:164`, пишется `build/write.ts:361`), ≥ 1.0 м и свободный подход по клеткам нава) и записать, какие проходы недоступны в XR. Высота: нав считает проход от 1.8 м (`nav/floor.ts:4–7`), капсула IWSDK — 2.0 м (сегмент 1.0 + радиус 0.5): места с потолком ниже 2.0 м (балки, лестницы) тоже в список недоступных.
- Невидимость забора проверять не нужно: локомотор берёт и невидимые меши (F12). `visible = false`, без материала в рендере.
- Забор строится один раз при загрузке; двери в него не входят (см. X4: `setCells` меняет только биты нава, на физику локомотора не влияет).
- Страж из спайка остаётся только счётчиком `offNav` (без отката), в `update()` без выделений (поля класса вместо массивов спайка).

### X3б (необязательный подэтап, не входит в минимум VR Start)

- Телепорт. `TeleportSystem` телепортирует на любую поверхность окружения с нормалью `y > 0.7` и nav не спрашивает (`teleport.js:85–119`): пол внутри огороженной мебели остаётся целью. Правило: хост оборачивает метод `teleport` у экземпляра локомотора, которым пользуется `TeleportSystem`; цель, которую нав запрещает (`probe.teleport` бросает), игнорируется без вызова оригинала. Проверяется цель на текущем этаже (`probe.teleport(x, z)` выбирает этаж относительно текущего `fy`, `walk.ts:35–38`; телепорт между этажами не поддерживается, лестницы идут стиком по рампам). Расстояние роли не играет, recenter головы и ходьба стиком в обёртку не попадают. Первым шагом X3 проверить, что обёртка перехватывает вызов; запасной путь — сверка позиции после кадра с телепортом (сигнал: `TeleportSystem` отпустил жест). Покадровый откат из спайка удаляется.
- Руки. В `iwsdk.config.json` hand tracking и locomotion включены, но телепорт и поворот рукой работают только через микрожесты, которые включает swipe вверх (кнопка 7 на правом геймпаде руки, 8 — выключает; `locomotion.js:229–251`). «Pinch-телепорт» из спайка не доказан: проверять реальную последовательность (swipe up → жест телепорта) через `xr set-input-mode hand` + `xr set-gamepad-state`; если эмулятор не воспроизводит — пункт остаётся «не доказано», проверка на Quest.
Тест: цель телепорта под кроватью → позиция игрока не меняется (запрещённый вызов не доходит до локомотора); цель на свободном полу проходит. Если перехват метода невозможен (поле локомотора приватно) — запасной путь выше, иначе подэтап снимается и записывается в долг.

Приёмка «без дрожания»: за 8 с непрерывного стика в стену/кровать число вызовов `setPlayerPosition` хостом = 0 и ни в одном кадре смещение игрока не меняет знак вдоль оси стика (нет откатов); `offNav = 0`.

Тесты X3: vitest — забор вокруг занятой клетки замкнут и сдвинут на `insetM`, у пустой комнаты забор совпадает со стенами; `xr-check.mjs` — стик вперёд из спавна спальни 8 с: игрок у изножья, `y` = пол ±2 см, `offNav = 0`.

## X4. двери и касания в XR

Зоны: `app/src/engine-host.ts`, при нужде `engine/src/runtime/doors.ts` (только экспорт), тесты.

- Створка двери — `RayInteractable` (правило `app/AGENTS.md`: не свой `Raycaster`); нажатие луча контроллера или луча руки (hand ray), касание пальцем (poke) вне объёма — в долг → то же, что в `main.ts:351–357`: DOM-событие `door_touch` (`detail.id`) для страницы и `bridge.touch(id)`, которое шлёт симуляции `{type:"touch", object:id}` (`bridge.ts:78–80`). Решает сим, дверь сама не двигается.
- Физика: створка — `LocomotionEnvironment` типа `kinematic`, поворот створки идёт через transform (для `KINEMATIC` локомотор обновляет матрицы, F12). Клетки двери исключены из забора X3; закрытая створка сама стоит в проёме, открытая — нет. `setCells` продолжает менять биты нава для сима и судьи `offNav`.
- Цикл дверей (`d.update`, `turnLeaf`) — в системе IWSDK, не в `requestAnimationFrame`. `LocomotionSystem` обновляет кинематику до движения игрока (`locomotion.js:221–227`): система дверей имеет приоритет выше (выполняется раньше) локомотора, иначе коллизия отстаёт на кадр. ELICS вставляет системы по возрастанию числового `priority` (`elics/lib/world.js:44–50`), у `LocomotionSystem` `-5` (`world-initializer.js:464–467`): система дверей получает число меньше `-5`. Порядок проверяется на рантайме первым шагом X4.

Фикстура: дверь спальни из мира спайка; `doorDefs` по умолчанию делает дверь открытой (`build/doors.ts:164–173`), поэтому тест сначала вызывает `close()` и ждёт 1 с; игрок ставится за 1.5 м до двери, стик вперёд 6 с. Закрытая: игрок остаётся ≥ 0.4 м от створки. Затем открыть (`openDoor`, поворот 0.6 с — константа в `doors.ts:2`, ждать 1 с) — игрок проходит и оказывается ≥ 1.5 м за дверью (допуск 10 см). Симуляция в проверке — заглушка на `localhost` (`?sim=<url>`), `xr-check.mjs` перехватывает `POST /event`; DOM-события хоста складываются в `__dreamerXr.doorEvents: string[]`.

Нажатие: система хоста следит за тегом `Pressed` на `RayInteractable` (`input/state-tags.js:33–67`; тег держится, пока кнопка зажата) и по **фронту** (появление тега, `queries.x.subscribe('qualify')`, не опрос) вызывает `door_touch` + `bridge.touch`. Открытие в тесте — публичный метод хоста `__dreamerXr.openDoor(id)` → `door.open()` из `EngineWorld.doors` (`turnLeaf` локален в `main.ts:266–277` и из скрипта не вызывается).

Тесты: удержание нажатия на 2 с даёт ровно одно `door_touch`; рукой нажать на дверь → в журнале хоста событие `door_touch` с её id **и** сообщение `touch` на `/event` симуляции с тем же id (два отдельных утверждения); открытая дверь пропускает игрока, закрытая — нет.

## X5. сцена в XR: режиссёр без камеры

Зоны: `engine/src/runtime/stage/index.ts` (только опция), `app/src/engine-host.ts`, тесты.

В шлеме камера = голова; двигать её силой нельзя (укачивает). Режиссёр в XR не ставит кадры, а работает вниманием.
- `startStage(..., { camera: null })`: режиссёр считает планы как сейчас (для журнала и фильма), но камеру не трогает. Десктоп и `?film=1` без изменений.
- Актёры, позы, места, взгляды, двери — как сейчас (всё это в мире, не в камере).
- Сейчас `createSubs` играет `r.audio` через `new Audio(url)` (`stage/subs.ts:9–14, 46–55`), не привязанный к актёру: XR-путь загружает URL как буфер, создаёт `PositionalAudio` на кости головы `who` и останавливает его при следующей реплике.
- Реплики: голос — `PositionalAudio` от головы говорящего; текст реплики — панель uikit у говорящего (skill `iwsdk-ui`), не HTML.
- Реализация `camera: null` в движке: `StageCtx.camera` сейчас обязателен и режиссёр читает `fov`/`aspect`, пишет позицию и `lookAt` (`stage/index.ts:18, 255–257, 698–725, 890–895`). Вводится интерфейс `StageView { fov: number; aspect: number; pos(): V3; apply(frame: {pos: V3; look: V3; fov: number}): void; writes: number }`. Десктопная реализация оборачивает `PerspectiveCamera` (`writes` растёт на каждый `apply`); XR-реализация хранит последний `frame` в памяти для журнала, оценки видимости и фильма, сцену не трогает, `writes` всегда 0. Все обращения `c.camera` в `stage/index.ts` заменяются на `StageView`.
- Статус: X5 — новый дизайн и может не успеть к VR Start; X1–X4 от него не зависят.
- Вход в сцену: игрок ставится в точку зрителя (точка общего плана режиссёра) через `setPlayerPosition` с затемнением; дальше ходит сам.

Тесты: vitest — XR-`StageView` за прогон `stage` на фикстуре даёт `writes === 0`, десктопный `writes > 0`, журнал кадров у обоих один и тот же; `xr-check.mjs` — за 10 с сцены мировая поза `world.camera` (с учётом XR-origin и трансформа `world.player`, не локальная) совпадает с позой головы эмулятора (±1 мм); для журнала и видимости XR берёт фактическую мировую позу головы, а `StageView.frame` остаётся запланированным кадром для фильма; источник реплики — событие `line` сима с полем `who`, `PositionalAudio` привязан к кости головы актёра `who`, расстояние до неё ≤ 0.3 м; панель — текст равен тексту реплики, ширина 0.4 м, над головой, лицом к игроку; десктопные тесты `stage` зелёные.

## X6. бюджет Quest и лист «десктоп | шлем»

Зоны: `app/tools/xr-sheet.mjs` (новый), `engine/src/budget.ts` (только чтение), отчёт.

- Лист: для каждой камеры из `geo.cameras` голова в IWER ставится в ту же точку и ориентацию (`xr set-transform` на `headset`), кадр рядом с десктопным `shots/` — правило AGENTS «скриншоты с тех же точек, один лист».
- `iwsdk browser profile` — десктопная неоткалиброванная диагностика времени кадра (`contract.js:1480`, на физическом шлеме не работает), это не fps Quest; draw calls, треугольники и текстуры дают render stats (`scene_get_render_stats`, `contract.js:2974`). Лимит треугольников на проп и сцену — `engine/src/budget.ts` (`TRI_PROP_BUDGET`); лимита draw calls в движке нет, X6 задаёт его числом (например ≤ 300 на сцену) и записывает как предположение до железа.
- `xr set-transform` ставит абсолютную позу в системе XR-origin и требует активную сессию (`contract.js:979`): лист пересчитывает камеру движка (мир, yaw 0 = +Z) в позу `headset` с учётом того, что игрок стоит через `setPlayerPosition` и поворот `+π` (F5).
- Настоящий Quest: `iwsdk-native-xr-test` после появления шлема или доступа VR Start. До того пункт остаётся открытым в `LESSONS.md`, не галочкой.
